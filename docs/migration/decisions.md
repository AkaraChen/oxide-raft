# Per-item decision records

Each record names the items it governs, the facts it rests on (with sources),
and the decision. Translators apply it; reviewers check it. Research notes with
full citations are in `research/`.

## D1. Command-line parsing: port commander 12.1.0

**Governs:** `crates/commander`; every command definition in `raft-cli` and
`raft-computer`.

**Facts.**
- The `raft` output contract includes commander's own text: help layout and
  wrapping (terminal width on a TTY, else 80), `error: unknown option '--x'`
  plus `(Did you mean --y?)` (Damerau-Levenshtein, max distance 3, similarity
  > 0.4), `missing required argument 'x'`, `option '--t <t>' argument missing`,
  excess positionals accepted silently, global `-p/--profile` accepted after
  subcommands, bare groups printing help then the `(outputHelp)` envelope with
  exit 1 (`research/cli.md` §2.2, §2.4; Appendix A has all 116 help outputs).
- `raft` uses `exitOverride` + a silenced `outputError`, and renders parse errors
  through its own envelope. `raft-computer` uses neither, so commander's default
  path is observable there too: the `error: …` line on stderr, then exit 1.
- clap cannot produce this text or these semantics byte for byte.

**Decision.** Port the used subset of commander 12.1.0 (`lib/command.js`,
`option.js`, `argument.js`, `help.js`, `suggestSimilar.js`, `error.js`) into
`crates/commander` as a translation. It must include parsing (short/long
options, `--opt=value`, combined short flags, `--`), parent options visible in
subcommands, `optsWithGlobals`, variadic arguments, custom option parsers with
accumulators, hidden options, `addHelpText("after")`, `preAction` hooks,
`version`, `exitOverride`, `configureOutput`, the automatic `help` subcommand,
suggestions, the help formatter, and the exit codes. Features neither CLI uses
(`choices`, `env`, `conflicts`, `implies`, `passThroughOptions`,
`enablePositionalOptions`, `allowUnknownOption`, `.usage()`, `.alias()`) are not
ported. Action handlers are async closures returning `Result`. Proof: the 116
help goldens plus the parse-error matrix from the oracle.

## D2. Contracts: a zod-compatible schema runtime

**Governs:** every translated zod schema (`agentApiContract.ts`,
`agentApiMessageContract.ts`, `daemonApiContract.ts`, `actionCards.ts`,
`externalAgentIntegration.ts`, `attachmentUploadContract.ts`,
`runtimeAccountUsage.ts`, `agentMigration.ts` if kept, and the two local ones in
`drivers/codex*.ts`).

**Facts** (`research/shared.md` §2).
- The agent-API client sends the **parsed** params, query, and body. `.trim()`
  (100+ uses), `.default()`, and `z.coerce.number()` change the bytes on the
  wire.
- Responses are parsed too. `z.object` strips unknown keys and re-orders the
  output to schema order; `passthrough` (155+ objects) keeps unknown keys after
  the known ones; `strict` rejects them. Formatters and `--json` output print
  the parsed result.
- zod v4.3.6's default issue messages reach agents verbatim (`raft action
  prepare`), and the daemon-API client derives `cause/path/expected_kind/
  actual_kind` from zod issue codes.

**Decision.** Build `raft_shared::schema`: a small runtime that operates on
`serde_json::Value` and mirrors the zod v4 combinators the closure uses
(`object`/`passthrough`/`strict`/`strictObject`, `string` with `trim`, `min`,
`max`, `regex`, `uuid`, `datetime`, `url`, `number`/`int`/`coerce`,
`boolean`, `literal`, `enum`, `array`, `record`, `union`,
`discriminatedUnion`, `optional`, `nullable`, `nullish`, `default`,
`transform` (identity branding only), `refine`/`superRefine` as closures,
`unknown`). `parse(&Value) -> Result<Value, ZodError>` produces the same output
value and the same `issues[]` (code, path, message, plus the codes' extra
fields) as zod 4.3.6. Each TS schema is translated line for line into builder
calls. Typed structs are deserialized from the parsed value where code needs
fields.

Proof: a golden corpus generated by the oracle. For every schema in the closure
and a set of valid and invalid inputs, record zod's `safeParse` result
(`tools/zod-golden/` script); the Rust runtime must reproduce each record. This
replaces hand-guessing zod messages.

Rejected alternatives: plain serde structs (cannot reproduce stripping plus
passthrough ordering plus issue text without per-schema hand code), and
JSON-Schema generation (loses transforms and messages).

## D3. JavaScript semantics helpers

**Governs:** `raft_shared::js`; every translated expression listed in
`mapping-guide.md` §6.

**Facts** (`research/shared.md` §6, `research/cli.md` §3.1, §7.5, §10).
Agent-visible text depends on UTF-16 lengths and slices (limits of 40, 80, 240,
500, and 4000; knowledge context 12–500), JS regex semantics (ASCII `\w\d\b`,
the `iu` case-fold quirk, lookahead in `raftRefs.ts`), `JSON.stringify` number
and key-order rules, `toISOString`, and lenient `new Date(string)`. V8
`JSON.parse` error text appears in `PROFILE_FILE_*` errors.

**Decision.** Implement `raft_shared::js` once, with oracle-generated golden
tests for each function:
- `utf16_len`, `utf16_slice`, `pad_start`/`pad_end`, `trim` (JS whitespace
  set, including U+FEFF);
- `JsRegex` over `regress`;
- `json_stringify`, `json_stringify_pretty`, and `json_parse` with V8 error
  messages (reproduce V8's `JSON.parse` wording for the error kinds reachable
  from a file read: unexpected token, unexpected end, expected property name,
  bad escape, and so on; golden-tested against Node 24);
- `number_to_string`, `to_fixed`, `to_number`, `parse_int`;
- `to_iso_string`, `date_parse` (V8 legacy parser subset);
- `encode_uri_component`;
- `Utf8StreamDecoder`;
- `sort_default`, `object_assign`.

Golden inputs include astral characters, lone surrogates, and edge numbers.

## D4. Errors that carry Node text

**Governs:** `raft_shared::node_compat`; any output path that prints a Node or
undici error message.

**Facts.** Visible examples: `ENOENT: no such file or directory, open '<p>'`
(profile errors), `EACCES: permission denied, …`, `Unexpected error: fetch
failed` for a raw fetch failure, and
`fetch failed for <url>: <class>/<CODE>` from the canonical proxy wrapper
(`research/cli.md` §3.2, §4.1, §4.2).

**Decision.** `node_compat` maps `io::Error` + syscall + path to Node's message
format (`<CODE>: <description>, <syscall> '<path>'`) using libuv's code and
description table for the codes that can occur (ENOENT, EACCES, EPERM, EEXIST,
ENOTDIR, EISDIR, ELOOP, EMFILE, ENOSPC, EROFS, EBUSY, ENOTEMPTY, EXDEV,
ETIMEDOUT, ECONNREFUSED, ECONNRESET, EPIPE, EADDRINUSE, ENETUNREACH,
EHOSTUNREACH, EAI_AGAIN/ENOTFOUND). A reqwest transport failure whose TS
counterpart was a raw `fetch` throw renders as `fetch failed`; the classified
form uses the source's `classifyFetchTransportFailure` rules on the reqwest
error chain (DNS, connect, TLS, timeout, proxy).

## D5. HTTP stack and proxies

**Governs:** `raft-cli` `client.rs`, `proxy.rs`, `agent_api_path.rs`,
`daemon_api_path.rs`; daemon `proxy.rs`, `daemon_fetch.rs`, `connection.rs`;
computer `api_client.rs`, `lib/api.rs`.

**Facts.** The CLI selects proxies with its own rules (`proxy.ts`: scheme-based
env precedence with `||`, NO_PROXY with host:port and suffix rules), and some
paths bypass proxies entirely (invokeV1, presigned PUT, bridge activity, device
auth). The daemon's WebSocket proxy precedence also covers `WSS_PROXY`/`WS_PROXY`.
The main CLI client has no retries and no timeouts (`research/cli.md` §4;
`research/daemon.md` §3).

**Decision.** reqwest with `.no_proxy()` everywhere. A proxy is attached per
request target by a translation of each package's `proxy.ts` (`getProxyUrlForTarget`,
`shouldBypassProxy`), caching one client per proxy URL as `buildFetchDispatcher`
does. For the WebSocket, CONNECT through the selected proxy
(`tokio-tungstenite` over a proxied `TcpStream`). No retries, timeouts, or
redirects beyond what the source does.

## D6. DaemonCore concurrency model

**Governs:** `raft-daemon-core`: `core.rs`, `agent_process_manager.rs`,
`agent_start_coordinator.rs`, `connection.rs`, `agent_credential_proxy.rs`,
`managed_mcp_runtime_proxy.rs`, `apps/*`.

**Facts** (`research/daemon.md` §10). All state is mutated from one JS event
loop, with invariants that rely on no await between check and set (start
dedupe maps, computer-control operation dedupe, start-queue invariants). There
are about 15 timer kinds per agent, held in tagged state unions so stale timers
cannot fire. Fire-and-forget promises complete later and mutate state.
Connection-generation fencing ignores stale sockets and retries. The credential
proxy's HTTP handlers wait on agent state (the freshness hold).

**Decision.** One actor task, `CoreActor`, owns everything the TS `DaemonCore`
and `AgentProcessManager` instances own. It receives a single `enum CoreMsg`
from:
- the connection (inbound server frames, open/close with a generation);
- child processes (stdout lines, stderr lines, exit, each tagged with
  `(agent_id, launch_id)`);
- timers;
- spawned futures (fire-and-forget completions);
- the proxy servers (requests that need core state, answered through a
  `oneshot`).

Timers are `tokio::time::sleep` tasks that post `CoreMsg::Timer { kind,
agent_id, launch_id, generation }`; the actor drops any timer whose generation
no longer matches, which replaces the TS "timer lives in the state union" rule
(the TS `timerStateTypes` typeproof becomes this check). The actor handles each
message to completion without awaiting other components, which preserves the TS
"no interleaving within a handler" guarantee. The work a TS handler performs
after an `await` becomes a continuation message.

Pure modules (`apmStateMachine`, `launchPhaseTransition`, `agentInbox*`, the
normalizers, `agentRuntimeInput`) stay plain functions and structs, with no
actor.

The credential proxy and the MCP proxy become services owned by `DaemonCore`
rather than module globals. Their registries live in the actor (or in an
`Arc<RwLock>` read by handlers, when the TS code reads them synchronously
without touching agent state).

The host hooks trait (`CoreHost`) has synchronous
`get_computer_lifecycle_acks()` / `get_computer_lifecycle_ready_acks()`, and
async `on_computer_control`.

The two credential-mint copies stay as two translations (translation-shaped
port; unifying them is a redesign). Reviewers verify both copies match their
sources.

## D7. Runtime drivers with in-parser I/O

**Governs:** `drivers/*.rs`, `drivers/runtime_session.rs`.

**Facts.** Codex (JSON-RPC app-server), grok (ACP), and kimi (wire) write to
the child's stdin from inside `parseLine`; grok defers `initialize` through a
microtask; parsers keep pending-request maps (`research/daemon.md` §5.1–5.2).

**Decision.** The Rust `RuntimeDriver` trait keeps the TS method set
(`probe`, `spawn`, `parse_line`, `encode_stdin_message`, `build_system_prompt`,
optional `create_session`). `parse_line(&mut self, line, &mut DriverIo) ->
Vec<ParsedEvent>`, where `DriverIo` queues stdin writes. The session task flushes
the queue after each call, in order. This replaces direct `child.stdin.write`
without reordering writes relative to reads. Grok's `queueMicrotask(initialize)`
becomes "queue the write immediately after spawn returns, before the first read",
which is the observable order of the TS code. Driver state lives in the driver
struct, which is owned by the session and is never shared.

## D8. CLI transport wrappers and the in-process CLI

**Governs:** daemon `drivers/cli_transport.rs`, `drivers/node_host_launch.rs`;
computer `__cli`.

**Facts.** Wrappers are wire-visible and byte-exact (bash, `.cmd`, `.ps1`,
the forwarding guard, the `slock-daemon-generated` marker). Under a SEA host
the wrapper runs `exec <execPath> __cli "$@"`. Credentials appear only in the
wrapper's exec prefix (`research/daemon.md` §5.3).

**Decision.** The Rust computer is treated as the TS "sea" host kind:
`detect_node_host_kind()` returns `Sea`, `slock_cli_path = "__cli"`, and the
wrapper command is `current_exe()`. The `slock` wrappers are still written,
because the daemon writes them for agents and agents may call `slock`; dropping
the CLI alias only means the Rust package ships no `slock` binary. The wrapper
bodies are produced by the same translated templates and golden-tested against
the oracle's `cliTransport` output.

`raft-computer __cli <args>` calls `raft_cli::run(args, env, io)` in-process,
with argv[0] semantics matching `runBundledRaftCli` (program name `raft`).
Node-host lookups (`resolveNodeHostLaunch` for codex's npm entry on Windows,
the opencli wrapper) are translated. On a Sea host they look for a system
`node` on PATH exactly as the TS code does, and otherwise raise the same
`NodeHostUnavailableError`.

## D9. Test porting and parity accounting

**Governs:** all `*_tests.rs`, `tools/test-parity`, `tests-waived.md`, and
`tests/golden/`.

**Decision.** As in `mapping-guide.md` §12. The parity tool reads upstream test
titles directly from the TS files: node:test manifests for the CLI, and
`vitest list --json` from the oracle for vitest packages. A test belonging to a
dropped feature is waived with that feature's name. A test that checks TS source

ported.

Golden capture scripts live in `tools/golden/` and are rerunnable against the
oracle.

## D10. Versions and identity strings

**Governs:** every crate's `Cargo.toml` version and every place that reports a
version or client name.

**Decision.** Crate versions equal the upstream package versions (cli 0.0.24,
daemon 1.0.25, computer 1.0.28, oar 0.0.7). Baked version strings such as

## D11. Computer service process model

**Governs:** `raft-computer` `service.rs`, `start_stop.rs`, `services/start.rs`,
`services/stop.rs`, `service_control.rs`, `macos_login_carrier.rs`, `cleanup.rs`,
`reset.rs`, `cli.rs` (`__service`).

**Facts** (`research/computer-service.md` §0, §2). Upstream 1.0.28 runs no OS
service manager. `__service` is a detached, self-spawned process tracked by
`computer/run/service.pid`. `stop` sends it SIGTERM (`TerminateProcess` on
Windows). Restart is an IPC self-handoff: the live service spawns a replacement,
waits until it attests the same managed set, then exits. macOS alone has a login
LaunchAgent, `build.raft.computer.login.<hash16>` (`RunAtLoad`, no
`KeepAlive`), with an owner marker that can hand the job to Raft Desktop. The
launchd, systemd, and scheduled-task definitions in `osSupervisor*.ts` exist
only to retire old installs.

**Decision.** Port the model that exists.
- Keep: the detached `__service`, `service.pid` semantics, the SIGTERM stop,
  the IPC self-restart handoff with its timeouts, and the macOS login carrier
  with an identical label, plist bytes, marker files, and the
  enable/disable readback. Drop only the K resume-deadline budget and
  `refreshCliLoginCarrierIfOwned`.
- Do not add systemd units, Windows tasks, or `KeepAlive`. Any of them would
  fight the self-restart handoff.
- Every binary location is `current_exe()` (canonicalized): the service spawn,
  the runner `__run` spawn, the `__cli` wrapper, and the plist
  `ProgramArguments[0]`. Keep the check that refuses a path under
  `<home>/computer/k/`.
- `__service` still accepts `--os-supervised <kind>` and ignores it, so stale
  definitions on user machines still boot a service.
- Detached spawn: on Unix, `setsid` with stdio appended to `service.log`; on
  Windows, `DETACHED_PROCESS | CREATE_NEW_PROCESS_GROUP | CREATE_NO_WINDOW`.
  This matches Node's `detached:true, windowsHide:true`.
- Windows keeps the upstream behavior. SIGTERM is a hard terminate, runners
  outlive the service and are adopted by the next one, and no Job Object is
  used.
- The supervisor is one task that owns every `RunnerRecord` (D6 style). A record
  is marked `starting` before any await in `spawn_child`, as in the source, and
  reconciles are coalesced.
- Installers (`install.sh`, `install.ps1`, SEA build, Hands release lookup) are
  not ported. Distribution is prebuilt binaries from this repo's releases.

## D12. Cross-implementation interop: IPC, locks, and state files

**Governs:** `internal/ipc_server.rs`, `internal/ipc_codec.rs`,
`lib/ipc_client.rs`, `service_ipc_seam.rs`, `concurrency.rs`,
`lifecycle_operations.rs`, `paths.rs`, and every state-file reader and writer.

**Facts** (`research/computer-core.md` §1 "Electron co-tenant", §2, §3, §7).
Raft Desktop embeds the TypeScript computer (`runService`/`runResident`) and
talks to the service over the same IPC. A Rust CLI can therefore meet a
TypeScript service on the same `RAFT_HOME`, and the reverse. The only guard is
the version-string comparison `SERVICE_VERSION_SKEW`.

**Decision.** Keep full wire and disk interop with upstream 1.0.28.
- IPC is byte-compatible: a u32 big-endian length, UTF-8 JSON, a 1 MiB cap, the
  same hello/request/response/event/cancel frames and error codes, the same
  socket path and modes (`run/service.sock`, dir 0700, socket 0600), the stale
  probe, and the Windows pipe name `raft-computer-<sha256(computerDir)[:16]>`
  with the default ACL and `first_pipe_instance(true)`.
- The mutation lock reimplements `proper-lockfile` 4.1.2 exactly: an mkdir
  lock at `<file>.lock`, an mtime refresh every `update` ms, staleness as
  configured by the source (`stale`), the same retry schedule, and
  compromised-lock detection. `lifecycle-operations.json.mutation.lock`
  follows the same rules. Golden-test it by running a TS lock holder (oracle)
  against the Rust contender, and the reverse.
- Every state file keeps its exact serializer: pretty or compact, trailing
  newline or not, key order (struct field order), and modes. That includes the
  `attach` write without `schemaVersion`. `attach` uses temp file plus rename,
  a deliberate hardening against the startup quarantine race. Record it in the
  review notes as the one intentional change.
- `RAFT_COMPUTER_PARENT_MUTATION_LOCK_HELD` and `…_SOURCE_SERVICE_PID`
  propagation, and their removal in `runnerChildEnv`, are translated exactly.

## D13. Dropped update surface: what remains observable

**Governs:** `cli.rs`, `status.rs`, `doctor.rs`, `resident_lifecycle_bridge.rs`,
`lifecycle_operations.rs`, `service_ipc_seam.rs`, and DaemonCore's
`computer:upgrade` handling.

**Decision.**
- The `upgrade`, `versions`, `operation`, `channel`, `__k-upgrade`,
  `__installer-converge`, `__legacy-supervisor-takeover`, and `__supervisor`
  commands are not registered. Invoking one gives commander's normal
  unknown-command error. They are not stubbed.
- The server can still send `computer:upgrade`. DaemonCore replies at once with
  `computer:upgrade:done {ok:false, error:"upgrade_unsupported"}` and records
  nothing, so no ready-ack stays pending. `computer:supervisor-mutations-v1`
  is still advertised, because the server routes restart through it.
- The IPC method `upgrade-start` stays registered and returns a structured
  rejection with the existing error code, so an old Desktop client gets a clean
  error.
- `status` prints `Upgrade: none in flight`. The doctor's K receipt check is
  removed, and the list of doctor checks shrinks accordingly.
- A leftover `action:"upgrade"` operation in `lifecycle-operations.json`,
  written by an earlier TypeScript install, can never complete here. The service
  retires it at startup with the same code path `retireCompletedUpgradeShutdownsFromLog`
  uses, triggered by the operation's action instead of by `upgrade.log`.
- The release channel file `computer/channel` is not read or written.

## D14. Shell environment capture before the async runtime

**Governs:** `raft-computer` `main.rs`, `shell_env_capture.rs`, `index.rs`.

**Facts** (`research/computer-core.md` §1 entry seam, §5). `index.ts` captures
the login-shell environment before the service graph loads, and replaces
`process.env` with it (protected keys are restored). `__print-env` must be
handled before any other setup. The shell comes from the passwd entry, each
argv element is single-quoted, and the framed output is parsed strictly.

**Decision.** `main()` runs the capture synchronously and applies it with
`std::env::set_var` before creating the tokio runtime or any thread. That is
the only point where `set_var` is sound. After that, `Env` (mapping guide §7) is
captured from the process environment and passed down. `__print-env` is
dispatched before anything else in `main`.

  it refuses to converge the login carrier while `/Applications/Raft
  Computer.app` exists without a marker, which prevents a double start.
- **O6. Raft Desktop co-existence.** D12 assumes the Rust CLI must interoperate
  with a TypeScript service run by Raft Desktop on the same home. If Desktop is
  not used on the same machine, D12 can be relaxed.
